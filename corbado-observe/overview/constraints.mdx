This page answers the question every engineering team asks first: **will this work with our stack, and what does it actually do to our application?**

## 1. What Observe requires

Very little, by design:

| Requirement | Detail |
| --- | --- |
| A JavaScript frontend | Observe runs in the browser. Any framework, any router, any rendering strategy. |
| A Corbado project | Provides your `Project ID` and `API Base URL`. |
| Outbound network access | The SDK sends batched events to the Corbado API. |

There is **no backend integration**, no server-side SDK, no IdP configuration and no change to your authentication logic. Observe works the same whether you run a commercial IdP, an open-source WebAuthn library, a custom implementation or an on-chain one.

## 2. What Observe never does

<Warning>
  Observe is telemetry only. It is not in the authentication path and cannot grant, deny, delay or alter a login.
</Warning>

- **Never blocks your login.** The SDK loads asynchronously and all tracking calls are guarded. An SDK failure, a blocked request or a missing configuration costs you telemetry — never an authentication.
- **Never changes flow behavior.** Instrumentation adds tracking calls at semantically correct points. It does not reorder, gate or modify authentication logic.
- **Never captures what users type.** No passwords, no form input contents, no session tokens. See [Data handling](#5-data-handling) below.

## 3. Platform support

| Platform | Status | Notes |
| --- | --- | --- |
| Web apps (SSR, SPA, MPA) | Supported | Same-document (SPA) route changes are observed, so a journey stays intact across a client-side router. |
| JavaScript-based frameworks (React, Vue, Svelte, Angular, Next.js, Nuxt, …) | Supported | No framework-specific integration required. |
| Web views inside native apps | Supported | The authentication surface must be web; the SDK runs in the web view. |
| Cross-origin iframes | Supported, with a requirement | The SDK must run in the frame where the WebAuthn ceremony happens. See [Iframes and RP IDs](#4-iframes-and-rp-ids). |
| Native iOS and Android apps | Contact us | Native app coverage is available through a dedicated engagement rather than a public SDK today. [Get in touch](mailto:support@corbado.com) if this is your primary surface. |

<Note>
  **JavaScript-based mobile frameworks** (for example React Native with Expo, or Ionic) authenticate through a web surface and are covered by the web integration wherever the login runs in a web context. Where a framework routes passkeys through a native platform API instead, the same "contact us" answer as for native apps applies.
</Note>

## 4. Iframes and RP IDs

If your authentication runs inside an iframe — a common pattern for embedded login, embedded wallets and "sign in with" experiences — two things matter:

- **The SDK must run in the frame that performs the ceremony.** `navigator.credentials` calls are observed in the document that makes them, not in the parent.
- **The iframe must be permitted to perform WebAuthn.** A cross-origin iframe needs the `publickey-credentials-get` and `publickey-credentials-create` permissions policy for passkeys to work at all. This is a requirement of your own passkey implementation, not of Observe — but it is the first thing to check when ceremonies appear to be missing.

See the Corbado Connect guide on [relying party IDs](/corbado-connect/helpful-guides/rpid-configuration/overview) for background on RP ID scoping.

## 5. Data handling

Observe is built for minimal data exposure.

**Never collected:**

- Passwords or any other typed input
- Form field contents
- Session tokens or credentials for your own system

**Collected:**

| Data | Purpose |
| --- | --- |
| Authentication journey events | Flows, steps, decisions, errors — the funnel itself |
| Device and client capability signals | Browser, operating system, device model where available, WebAuthn capability flags such as platform-authenticator availability |
| WebAuthn ceremony data | Ceremony lifecycle, mediation, authenticator and credential metadata (AAGUID, transports, backup state, discoverability) |
| A user reference, if you provide one | Links journeys to your own user entity — see [Users](/corbado-observe/tracking/user) |
| Tags you define | Your own dimensions such as country, channel or experiment variant — see [Tags](/corbado-observe/tracking/tags) |

<Warning>
  WebAuthn responses are inherently identifying: they contain credential IDs, user handles, challenges, signatures and authenticator data. Observe collects the fields it needs to produce authenticator and credential insight. If you must not send user handles or credential IDs to a processor, raise this before integration so the collection profile can be scoped accordingly.
</Warning>

**You control identity.** The user reference is a value you pass. If you pass a pseudonymous or hashed identifier, Observe never sees a real user ID.

## 6. Autocapture: what it hooks and where it stops

Autocapture observes the browser surfaces that authentication runs through:

- The **DOM tree**, to locate the fields and buttons your authentication uses, including across shadow-DOM boundaries
- **DOM events** (`focus`, `blur`, `input`, `click`, `submit`) on those elements, for the low-level interaction signals
- `navigator.credentials.get()` and `create()` for **WebAuthn ceremonies**
- `fetch` and `XMLHttpRequest`, limited to URLs that the configured match rule selects — all other traffic is ignored
- **Same-document navigation** for SPA route changes

Known limitations:

| Limitation | Effect |
| --- | --- |
| **Password managers that lock WebAuthn accessors** | Some extensions replace `navigator.credentials` with non-writable accessors. 1Password is a tested example. Autocapture then reports its WebAuthn capture as unavailable and rolls back cleanly: **passkey operations continue to work normally**, but those ceremonies produce no WebAuthn telemetry. |
| **Another integration overwriting the same surface** | If a third-party script replaces a patched method without forwarding through it, capture is displaced for that surface. The application call still succeeds; the telemetry is lost. |
| **Concepts Autocapture will not infer** | Enrollment intent, conditional-UI spec types, known-identifier state and user-vs-system actor are deliberately not guessed. Use [precision tracking](/corbado-observe/overview/integration-paths) where you need them. |

## 7. Browser support

The SDK targets **ES2019** and assumes ES2019-era runtime primitives. The current test suite covers current **Chromium**, **Firefox** and **WebKit**, including password-manager simulation and virtual WebAuthn in Chromium.

<Note>
  If you need a documented support floor for older Android WebViews, legacy Edge or specific enterprise browser versions, ask us — the tested matrix is expanding and we would rather give you a precise answer than a marketing one.
</Note>

## 8. Storage and consent

The SDK stores a session identifier client-side to correlate the events of one journey. You choose the mechanism at initialization:

| Option | Behavior |
| --- | --- |
| `storage: "local"` | Uses browser storage on the current origin. |
| `storage: "cookie"` | Uses a cookie, with an optional `cookieDomain` for correlation across subdomains. |

Observe stores no marketing or advertising identifiers and does no cross-site tracking. Whether your consent management platform needs to gate the SDK depends on your own legal assessment — if it does, initialize Observe after consent and the journeys before that point are simply not recorded.

## 9. Projects and environments

Keep **environments in separate projects** — production, staging and development should not share a project, because mixed data makes funnels meaningless.

Use [applications](/corbado-observe/tracking/applications) to separate *channels* of the same product (web, native app), and [tags](/corbado-observe/tracking/tags) for further dimensions such as country or experiment variant.

## 10. Hosting

Observe runs on Corbado's public cloud by default. Dedicated instances in a specific region are available for enterprise deployments — relevant if you have data residency requirements. [Contact us](mailto:support@corbado.com) to discuss options.
