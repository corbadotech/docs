## Acceptance criteria

| Benchmark as | Expected adoption impact |
| --- | --- |
| Strategy | Mid |

This flow covers passkey creation as part of registering a new account. Its reach is high among new users but does not enroll existing accounts.

| ID | Level | Acceptance criterion | How to verify |
| --- | --- | --- | --- |
| **W2.7-AC01** | Core | Before passkey creation, assign the new account its permanent WebAuthn user handle. If signup still uses a temporary account record, persist a reliable mapping from that handle and the returned credential ID to the final account. | Create a passkey before the final account record is completed, then finish signup and sign in with it. Add another passkey later. Both credentials resolve to the final account and use the same WebAuthn user handle. |
| **W2.7-AC02** | Core | When the chosen signup method is sufficient to authorize passkey creation, create the passkey before asking the user to verify a separate fallback such as a phone OTP. If it is not sufficient, complete the required verification first. A passkey created for a pending account becomes usable only after the required signup verification succeeds. | Test one signup policy that permits creation before fallback verification and one that requires verification first. In the first case, abandon the OTP and confirm that the pending account cannot sign in, then complete it and confirm that the passkey becomes usable. In the second case, passkey creation does not start before verification. |
| **W2.7-AC03** | Core | When the passkey is used as the account's second factor, signup also completes a usable fallback for that factor. A collected phone number or email address counts only after its OTP or verification link succeeds. | Create the passkey and abandon fallback verification. The account is not considered ready for passkey-based MFA. Complete verification and confirm that the configured fallback can be used when the passkey is unavailable. |
