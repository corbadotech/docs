## Acceptance criteria



| Benchmark as | User reach |
| --- | --- |
| Strategy | High |

| ID | Level | Acceptance criterion | How to verify |
| --- | --- | --- | --- |
| **W1.1-AC01** | Core | Show One-Tap only after the user has successfully created or used a passkey for this account in the current browser profile. Any successful creation entry point counts, including passkey management. Opening or cancelling creation, or creating a credential that the server fails to register, does not count. | Complete passkey creation from account management and every other supported creation entry point, then complete a passkey login. Each successful server registration or login makes One-Tap eligible. Cancellation, failed server registration, a new browser profile, cleared site data and server-known revocation do not. If a credential is deleted only inside a provider, a stale offer may remain because the application cannot know about that deletion; the user must still reach a safe fallback. |
| **W1.1-AC02** | Core | Show enough account information for the user to recognize the intended account. Apply masking where required, but keep different accounts distinguishable. The hint alone cannot enable login without a valid passkey assertion. | Use two accounts in one browser profile and each configured masking mode. Confirm that the hints remain distinguishable and that neither hint can authenticate without a valid assertion for the intended account. |
| **W1.1-AC03** | Core | The One-Tap hint selects the account, not one specific credential. Every active passkey accepted for that account remains eligible, so the user can complete login with any available passkey. | Create several active passkeys for one account across the supported providers and devices. Inspect the request and complete One-Tap login with each passkey, including supported cross-device routes. No active credential is pinned or omitted. |
| **W1.1-AC04** | Core | Treat browser-stored account state only as an account hint; it never authenticates the user or bypasses assertion verification. | Modify, forge and delete the stored hint, then attempt login without a valid assertion. No state change should grant access. |
| **W1.1-AC05** | Core | Provide a directly reachable "Use another account" or equivalent path before authentication. | Render One-Tap for one account and switch to a second account without completing the first account's ceremony. The second account's normal login path should be usable. |
| **W1.1-AC06** | Core | Do not open a passkey prompt before the user activates the One-Tap action. | Load and focus the login page without activating One-Tap. No modal credential request should appear. |
| **W1.1-AC07** | Core | Bind a returned assertion to the intended account independently of the browser-stored account hint. | Attempt to complete the ceremony with a credential belonging to another account and with a modified hint. Neither case may authenticate as the intended account. |
| **W1.1-AC08** | Core | The One-Tap entry state does not show or require an identifier field. The user can start passkey login for the hinted account directly, while "Use another account" opens the normal identifier flow. | Render One-Tap for an eligible account. Confirm that its passkey action starts the ceremony directly and that "Use another account" opens identifier entry without first starting a passkey request. |
| **W1.1-AC09** | Core | After the user cancels or aborts One-Tap, the product does not open another passkey prompt automatically. It either shows the identifier flow with the available fallback choices or proceeds directly to the configured fallback for the hinted account. | Cancel the One-Tap ceremony on the first and a repeated attempt. Confirm that no new ceremony starts automatically and that the configured identifier-first or direct-fallback route remains usable. |
| **W1.1-AC10** | Quality | Include stored transport hints with each account-scoped credential descriptor when available. They help the browser offer suitable routes after One-Tap is activated, such as phone/QR for `hybrid` or a security key for `usb` or `nfc`. Keep the One-Tap icon generic because all active passkeys remain eligible and the stored transports do not identify which route or password manager will be used. | Register credentials with different recorded transports and inspect the generated request options. Each descriptor retains its stored values, while the One-Tap action does not present itself as a specific security-key, phone or password-manager route. |

### References

- **Relevant criteria:** `W1.1-AC03`, `W1.1-AC04`, `W1.1-AC06`–`W1.1-AC10`. [Web Authentication: An API for accessing Public Key Credentials: Level 3](https://www.w3.org/TR/webauthn-3/) defines authorization gestures, account-scoped requests, credential descriptors and transports, account binding and server-side assertion verification.
- **Relevant criteria:** `W1.1-AC01`–`W1.1-AC02`, `W1.1-AC05`–`W1.1-AC06`, `W1.1-AC08`–`W1.1-AC09`. [One-Tap Login: Seamless Passkey Authentication](https://docs.corbado.com/corbado-connect/features/one-tap-login) documents the returning-user pattern, recognizable account hint, explicit activation, account switching and the route back to normal login; it supports the flow shape, not a vendor requirement.
- **Relevant criteria:** `W1.1-AC01`. [How to get high passkey adoption in login flows](https://www.corbado.com/blog/passkey-login-best-practices) provides practical guidance for eligibility-driven presentation. Its reported rates provide context, not acceptance thresholds.
- **Relevant criteria:** `W1.1-AC09`. [Passkey fallback and recovery](https://www.corbado.com/blog/passkey-fallback-recovery) supports deliberate fallback after a cancelled passkey attempt without automatic reprompting.
